STEP 7 — DIRECT REQUEST VALIDATION
FINDING 1.3 — CUSTOMER ID BYPASS ON SIGN-IN

## BEFORE FIX

Endpoint:
POST /api/auth/signin

Test:
A direct API request was sent with the temporary test account's email and password, deliberately omitting customerId.

Result:
HTTP STATUS: 200

Response:
{
  "success": true,
  "user": {
    "id": "[REDACTED]",
    "customerId": "6231",
    "name": "Evidence 09 Test",
    "email": "evidence09@example.com",
    "role": "CUSTOMER"
  }
}

Conclusion:
The server authenticated the customer without requiring customerId.
This confirms that the frontend requirement was not enforced by the sign-in API.

## AFTER FIX:

### Test 1 — Customer ID omitted

Request:
POST /api/auth/signin

Supplied:
- Email: evidence09@example.com
- Password: TestPassword2026!
- Customer ID: Omitted

Actual result:
HTTP STATUS: 401

Response:
{
  "success": false,
  "error": "Invalid Customer ID or password."
}

Conclusion:
The server now rejects customer sign-in when Customer ID is missing.

### Test 2 — Correct Customer ID supplied

Request:
POST /api/auth/signin

Supplied:
- Email: evidence09@example.com
- Customer ID: 6231
- Password: TestPassword2026!

Actual result:
HTTP STATUS: 200

Response:
{
  "success": true,
  "user": {
    "id": "[REDACTED]",
    "customerId": "6231",
    "name": "Evidence 09 Test",
    "email": "evidence09@example.com",
    "role": "CUSTOMER"
  }
}

Conclusion:
The server accepts legitimate customer sign-in when the correct Customer ID and password are supplied.



**Finding:** 1.1 — Single-word name bypass

**Endpoint:** POST /api/auth/signup

### Test request

A direct API request was sent with the name `Madonna`, bypassing frontend validation.

```cmd
curl.exe -i -X POST http://localhost:3000/api/auth/signup -H "Content-Type: application/json" -d "{\"name\":\"Madonna\",\"email\":\"evidence11@example.com\",\"password\":\"TestPassword2026!\",\"confirmPassword\":\"TestPassword2026!\"}"
```

### Actual result

HTTP status: `400 Bad Request`

Response:

```json
{
  "success": false,
  "error": "Please enter your full name (at least two names).",
  "errors": {
    "name": [
      "Please enter your full name (at least two names)."
    ]
  }
}
```

### Conclusion

The server-side Zod validation now enforces the minimum two-word full-name requirement. A direct API request containing a single-word name is rejected before account creation.

Live endpoint verification passed.

## Finding 1.2 — Terms and Conditions Agreement Bypass

**Endpoint:** POST /api/auth/signup

### Test 1 — Agreement omitted

Request supplied:
- Valid two-word name
- Valid email
- Valid password
- Matching password confirmation
- `agreeToTerms` omitted

Actual result: HTTP 400 Bad Request

Error:
`You must agree to the Terms and Conditions to create an account.`

Conclusion: The server rejects registration when agreement is omitted.

### Test 2 — Agreement explicitly false

Request supplied:
- Valid registration details
- `agreeToTerms: false`

Actual result: HTTP 400 Bad Request

Error:
`You must agree to the Terms and Conditions to create an account.`

Conclusion: The server rejects registration when the user has not agreed.

### Test 3 — Agreement explicitly true

Request supplied:
- Name: Evidence Terms
- Email: evidenceterms@example.com
- `agreeToTerms: true`

Actual result: HTTP 201 Created

Response confirmed:
- `success: true`
- Account created successfully
- Customer ID: 1542
- Role: CUSTOMER

Conclusion: The server accepts valid registration when explicit agreement is supplied.

**Final result:** All three live API tests passed. The server now enforces explicit Terms and Conditions agreement.

Note: The HTTP response included a session cookie. Its value has been intentionally excluded from this evidence file.
